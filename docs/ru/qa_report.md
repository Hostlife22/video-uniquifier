<a id="qa-report"></a>

# Отчёты качества

Каждый `video-uniq run` (если только не `--no-qa`) создаёт два артефакта рядом с файлом вывода:

```
output.mp4
output.mp4.qa.json    # machine-readable
output.mp4.qa.html    # human-readable, with heatmaps + verdict banner
```

`video-uniq qa <input> <output>` генерирует ту же пару для существующей пары вход/выход без повторного кодирования.

<a id="whats-measured"></a>

## Что измеряется

Для одной пары (вход, выход) отчёт оценивает три независимые оси: корректность медиа, воспринимаемое качество и диагностическое сходство. Опциональные механизмы метрик деградируют плавно, но отсутствующий или повреждённый медиапоток является ошибкой корректности и создаёт `INVALID`, никогда не выдавая обычного вердикта метрики.

> **Новое с версии v0.8.0**: опциональные оценки семантической схожести SSCD
> (`video-uniq qa --sscd`,
> требует `[ml]` дополнительно) и событий повторной попытки с ограничением target-VMAF для
> профилей, которые выбирают `target_vmaf`. См. разделы SSCD + target-VMAF
> ниже.

<a id="file-level"></a>

### На уровне файла

|Поле|Источник|Значение|
|---|---|---|
| `input_md5`, `output_md5` |потоковый md5 (чанки по 4 МБ)|точная идентичность байтов (разная для каждого успешного запуска — совпадает только при `--new-variant=false` возобновлении точно того же плана)|
| `input_size_bytes`, `output_size_bytes` |файловая система|проверка корректности бюджета битрейта|
| `input_duration_sec`, `output_duration_sec` |ffprobe|должно совпадать в пределах ±0,5 с; `duration_match` — это булево значение|

До вычисления хэшей или выборочных метрик QA проверяет оба файла. Автоматические отчеты при запуске/пакете/GUI также получают существующий `Plan` и повторно используют окончательный медиадоговор для топологии потока, временной метки и проверок HDR/SDR. Отдельное QA применяет консервативные проверочные пары. Основное видео кандидата и все аудиопотоки затем декодируются до EOF с FFmpeg `-xerror -err_detect explode`, так что поврежденный невыборочный хвост становится
`correctness: full output decode failed` в `notes[]`, а статус — `INVALID`.

Независимо от генерации отчета, `run_full` выполняет полное декодирование как обязательный последний этап публикации для CLI, GUI, веба и распределенных воркеров. Это также применимо к `--no-qa`. Автоматические отчеты после выполнения повторно используют успешный этап вместо декодирования того же вывода дважды; автономный `video-uniq qa` выполняет собственное декодирование.

<a id="visual-similarity"></a>

### Визуальное сходство

|Поле|Источник|Диапазон|Значение|
|---|---|---|---|
| `phash_samples` | — |обычно 120|сколько кадров было выбрано|
| `phash_distance_min`, `_mean`, `_max` |imagehash.phash на `samples` кадрах|0..64 бита|расстояние Хэмминга между парными кадрами|
| `phash_similarity` | `1 - mean_distance / 64` | 0..1 |агрегированное; больше = ближе к исходнику|
| `vmaf_mean` |ffmpeg `libvmaf`| 0..100 |восприятие качества по сравнению с источником; null, если libvmaf отсутствует или необработанное HDR поле не поддерживается|
| `ssim_mean` |ffmpeg `ssim`| 0..1 |индекс структурного сходства; null, если отключено|

<a id="audio-similarity"></a>

### Аудио сходство

|Поле|Источник|Диапазон|Значение|
|---|---|---|---|
| `audio_fp_similarity` |chromaprint Жаккард по подотпечаткам uint32| 0..1 |пересечение установленных декодированных кодов; не идентичность байтов|
| **`audio_fp_hamming_per_frame`** |chromaprint XOR + popcount, парные кадры, среднее|0..32 бита|внутренняя диагностика расстояния на уровне битов|
| **`audio_fp_match_confidence`** | `1 - hamming_per_frame / 32` | 0..1 |наследуемый эвристический нормализованный коэффициент сходства; не откалиброванная достоверность|

Все три поля отпечатков получены из одного извлечения отпечатков на файл, а не из шести `fpcalc` процессов на отчет. Для источников длиной более 600 секунд пять окон по 120 секунд охватывают начало, середину и конец и объединяются перед созданием отпечатка; `notes[]` фиксирует, что использовалось стратифицированное покрытие.

`audio_fp_similarity` — это индекс Жаккара (`|A ∩ B| / |A ∪ B|`) для декодированных наборов 32-битных суб-отпечатков. Совпадение кода точно не означает идентичность байтов; повторное кодирование может сохранять коды. Порядок не учитывается, и низкий балл не доказывает слышимое повреждение. Хэмминг — это другой диагностический метод отпечатков, а не модель человеческого восприятия. Ни одна из метрик не является откалиброванной уверенностью или предсказанием закрытой системы.

Поля Хэмминга были введены в версии v0.3.3. Их старые названия сохранены для совместимости со схемой, но они не являются ключевым показателем системы авторских прав или вероятностью. Интерпретируйте их только относительно закрепленного источника/корпуса и версии инструмента:

|`hamming_per_frame` (бит)|Интерпретация|
|---|---|
|низкое значение|сопряженные коды Chromaprint ближе для этого эксперимента|
|среднее значение|результат требует прослушивания и проверки по временной шкале/синхронизации|
|высокое значение|Сопряженные коды различаются сильнее; это не говорит ничего о слышимости или внешней системе|

<a id="plan-registered-metrics-v15-rfc-12"></a>

### Метрики по эталону из плана обработки (v1.5, RFC №12)

Для длинных файлов, необработанный и зарегистрированный VMAF применяют существующую автоматическую политику выборки (приблизительно четыре оцененных кадра в секунду). Зарегистрированная выборка использует выходную длительность и каденцию, а ее интервал записан в заметках отчета. Отменяемый VMAF/SSIM также выдает FFmpeg прогресс для сторожевого таймера бездействия; нулевой мультиплексор записывает на портативное нулевое устройство. Вся временная шкала декодируется; это выборка оценок VMAF, а не сокращенная эталонная или непрерывная послекадровая оценка качества. Короткие файлы сохраняют оценку по кадрам. Эта политика не устанавливает жесткого ограничения на FFmpeg или память полной QA.

Исходные показатели/метрики выше намеренно сохраняют своё историческое значение. Когда автоматическая проверка качества при запуске/пакете имеет точно выполненный `Plan`, она дополнительно воспроизводит существующую графику фильтров видео с восстановленным зерном запуска и зернами для каждого сегмента в временный без потерь FFV1 эталон. Зарегистрированное сравнение VMAF/SSIM сбрасывает обе временные шкалы локально перед оценкой, поэтому намеренное обрезание, зеркалирование, изменение времени или детерминированное выпадение кадров является частью эталона, а не классифицируется как повреждение кодека.

|Поле|Диапазон|Инженерное значение|
|---|---:|---|
| `vmaf_registered_mean` |0..100 или null|Качество кодирования/порождений относительно преобразованного эталона|
| `ssim_registered_mean` |-1..1 или null|Структурное качество относительно преобразованного эталона|
| `sscd_registered_mean` |-1..1 или null|Ограниченное монотонное сходство представлений; выходные кадры не могут быть повторно использованы|
| `audio_fp_registered_hamming_per_frame` |0..32 или null|Упорядоченное расстояние Chromaprint после выравнивания с ограниченным глобальным смещением и линейным дрейфом|
| `registration.reference_mode` | `plan_transformed` |Указывает, что эталон взят из точного воспроизведения плана|
| `registration.plan_hash`, `run_seed` |происхождение|Привязывает отчет к завершенному плану и стохастической реализации|
| `registration.video`, `.audio` |объект или null|Смещение/дрейф, сравнение образцов, покрытие, доверие и примечание о доступности|

Эти поля остаются диагностическими: вердикт продолжает использовать корректность и неизмененную политику качества сырья до тех пор, пока лицензированный корпус природного контента не установит зарегистрированные пороговые значения. Аудио/SSCD с низким перекрытием отклоняется вместо возврата вводящего в заблуждение хорошего значения. Зарегистрированный VMAF закрывается для сохраненного HDR вместо интерпретации значений кода PQ/HLG с использованием модели SDR; вывод HDR→SDR может быть оценен после явного тонового отображения, потому что оба зарегистрированных входа тогда являются SDR.

Например, расширенный эксперимент с 4K контентом высокой естественности дал сырое значение VMAF 3,73 и VMAF с регистрацией плана 93,81 в той же ячейке. Первый включает различие с исходной сценой/таймлайном; второй сравнивает кодирование с преобразованным эталоном. Одного лишь числа недостаточно для выпуска в производство. Запуск корпуса записывает полноту измерений отдельно от вердикта QA и принятия человеком; его статус `measured` не является проходным по качеству.

Общественные нуллабельные объекты корректности/громкости и необязательные политики качества реализованы в соответствии с принятым RFC #21; см. раздел явных доказательств ниже.

Генерация эталона может быть отменена и защищена как свободным пространством, так и
`VIDEO_UNIQ_REGISTERED_REFERENCE_MAX_BYTES` (по умолчанию 40 ГиБ). Если консервативная оценка FFV1 превышает этот лимит, зарегистрированные видео-метрики становятся недоступными с явной записью `notes[]`; необработанное QA продолжается. Предоставьте больше временного пространства и установите переменную сознательно для длительных прогонов. Справочные эмбеддинги SSCD кешируются в `VIDEO_UNIQ_QA_CACHE_DIR` или в кэше QA для каждого пользователя с использованием исходного контента, канонического профиля, плана/сиды, версии FFmpeg/инструмента/модели, сетки выборки и дайджеста закодированной ссылки; повреждённые записи восстанавливаются атомарно.

<a id="sscd-semantic-similarity-v080-r4-opt-in"></a>

### Семантическое сходство SSCD (v0.8.0 R4, опционально)

Заполняется только при передаче `video-uniq qa --sscd`. Требуется дополнительный пакет `[ml]` (torch + torchvision). Первый запуск загружает примерно 94 МБ весов модели в
`~/.cache/video_uniquifier/models/`; последующие запуски используют кэш. Подробное описание в [`docs/en/sscd.md`](sscd.md).

|Поле|Источник|Диапазон|Значение|
|---|---|---|---|
| `sscd_mean` |среднее косинусное значение по парным эмбеддингам| -1..1 |диагностика копии изображения|
| `sscd_min` |минимальный выборочный косинус| -1..1 |наименее похожая пара выборок|
| `sscd_per_frame[]` |упорядоченные косинусы на нормализованной сетке средних точек| -1..1 |выборочные доказательства, а не локализация сегмента|

`notes[]` записывает наивысший выбранный косинус и его запрошенные временные метки источника/выхода, количество пар, официальный хэш модели и предобработку. Короткая вставка соответствия между образцами может быть пропущена. SSCD не обладает качеством для человека или Content ID.

<a id="target-vmaf-retry-events-v080-r5"></a>

### События повторной попытки Target-VMAF (v0.8.0 R5)

Профили, которые устанавливают `target_vmaf`, инициируют повторную попытку во время выполнения, когда сегмент оказывается ниже целевого значения. Это живые `RunEvent` записи, которые потребляют вызовы CLI/GUI; они в настоящее время не встроены в `QAReport` JSON:

|Поле|Значение|
|---|---|
| `target_vmaf.payload.segment` |какой сегмент был оценен|
| `target_vmaf.payload.attempt` |попытка кодирования с нулевой базой (`0` — это начальное кодирование)|
| `target_vmaf.payload.vmaf` |VMAF фактически измеренный, или null, если оценка не удалась|
| `target_vmaf.payload.crf` |подсказка качества, эквивалентного программному обеспечению, для попытки|
| `target_vmaf.payload.target` |настроенная цель|
| `target_vmaf_failed.payload.best_attempt` |попытка с нулевым индексом сохранена на диске|

`target_vmaf_max_retries` ограничивает цикл. После исчерпания сегментатор сохраняет кандидата с наивысшим баллом и выдает `target_vmaf_failed`.

Оценщик обратной связи в настоящее время использует обычный фрагмент источника. Предварительная проверка отклоняет
`target_vmaf` с геометрией, рестаффингом, зеркалированием, наложениями, субтитрами или тонмаппингом, поскольку эта пара не зарегистрирована, и повторные попытки CRF не могут сделать оценку сходящейся. Используйте повтор этой исходной нарезки только для поддерживаемой неизмененной эталонной области; это отдельно от QA, зарегистрированного после выполнения плана.

<a id="legacy-self-similarity-heuristic-v02"></a>

### Устаревший эвристический метод самоподобия (v0.2+)

|Поле|Источник|Значение|
|---|---|---|
| `cid_predict_self` |максимальное значение взятого pHash и доступного агрегированного префиксного аудио Jaccard|0..1; внутренняя эвристика самоподобия (устаревшее имя поля)|
| `weakest_chunk_sec` |argmax по `chunk_similarities[].combined`|(start_sec, end_sec) фрагмента, наиболее похожего на источник|
| `chunk_similarities[]` |выборка окон на общем префиксе: `{start_sec, end_sec, visual, combined}`, необязательный `audio`|управляет HTML-тепловой картой|
| `corpus_matches[]` |сравнение с `video-uniq corpus` записями|`{id, path, visual, audio, combined}` для файлов выше порога|

`cid_predict_self` не является ни вероятностью, ни предсказателем YouTube Content ID. Это проекта-специфичный диагностический индикатор максимального сходства, полезный для сравнений регрессии и диагностики самоколлизий на принадлежащих или лицензированных производных. Не используйте его как производственный критерий прохождения/непрохождения без проверки на конкретном корпусе.

<a id="notes-assessment"></a>

### Заметки + оценка

|Поле|Значение|
|---|---|
| `notes[]` |предупреждения о недоступных бэкендах (например, «fpcalc не в PATH»)|
| `duration_match` |bool — входные/выходные длительности в пределах ±0,5 с|

CLI и HTML показывают независимые оси:

- **Корректность** — `VALID`, `INVALID` или `NOT_VERIFIED`. Первостепенное значение имеют топология, продолжительность, PTS первого видео, заявленный цвет/контракт HDR и полное декодирование.
- **Качество** — `PASS`, `WARNING`, `FAIL` или `UNAVAILABLE`, на основе VMAF/SSIM.
- **Визуальное сходство** — `LOW`, `MODERATE`, `HIGH` или `UNAVAILABLE`, на основе выборочного pHash и явно диагностируемое.

Общий статус вывода — `INVALID` при сбое корректности, в противном случае зеленый/желтый/красный определяется только на основании доказательств качества. Сходство никогда не компенсирует плохое качество и никогда не превращает корректный, высококачественный вывод в сбой.
Существующая схема JSON `QAReport` остается совместимой с добавлением; устаревшие `notes[]` остаются на месте, а версия 1.6.0 добавляет структурированные доказательства в соответствии с [RFC #21](https://github.com/Hostlife22/video-uniquifier/issues/21).

<a id="explicit-evidence-and-optional-gates-v160"></a>

## Явные доказательства и необязательные проверки (v1.6.0)

- `correctness`: `status` (`passed`, `failed`, `not_verified`), `scope` (`plan_contract` или `pair_contract`), `failure_codes`, `full_decode_status`, `note`. Прохождение означает, что проверялись только заявленный контракт и полная декодировка. Это
  **не** подтверждает внутреннюю синхронизацию губ, слышимые переходные сигналы или визуальное качество. Без Плана доступен только консервативный парный контракт. Устаревший `duration_match` по-прежнему сравнивает длительность исходного и выходного материала; принятые изменения скорости используют ожидаемую длительность по Плану для структурированной корректности и вынесения вердикта вместо этого.
- `loudness`: измерение `status`, `streams` и `note`. Каждый выходной аудиопоток сообщает о своем абсолютном `stream_index`, `integrated_lufs`, `true_peak_dbtp`, `method`, измерении `status` и `note`. К измеряемому сигналу не применяется сведение или нормализация. Измерения тишины/ниже порога с отрицательной бесконечностью становятся нулевыми; недопустимые значения NaN/+бесконечность не отмечаются как проверенные. `passed` означает, что сканирование завершено, **но не** то, что цель громкости, клиппинг/фаза или прослушивание прошли. По умолчанию: `not_verified` (сканирование не запрошено); используйте `--loudness` для полного сканирования каждого выходного трека. На длинных фильмах это может занять значительное время.
- `quality_policy`: необязательный `domain` (`raw` или `registered`), `min_vmaf` (0–100) и `min_ssim` (-1–1). Null означает, что старые эвристические диапазоны остаются активными. Когда минимумы запрашиваются явно, эти минимумы в выбранной области определяют ось качества; **все** запрошенные метрики должны быть доступны, конечны и соответствовать требованиям. Зарегистрированные пороги также требуют наличия пригодных видеодоказательств, а не только числового значения. Они не устанавливают универсально откалиброванную цель качества.

Только пример — это пороги, выбранные оператором, а не стандартные настройки для производства:

```bash
video-uniq qa source.mkv output.mp4 --plan-json plan.json --quality-domain registered \
  --min-vmaf 90 --min-ssim 0.98 --loudness
```

Явный сбой шлюза или неподтвержденная корректность записывают JSON/HTML и завершают работу с кодом **2**. Недопустимые комбинации (такие как `--fast-qa --min-vmaf 90`, `--no-ssim --min-ssim .9` или зарегистрированные шлюзы без Плана) завершаются до выполнения дорогостоящих метрик. Необработанные шлюзы VMAF отклоняют HDR-пары: `phone_model=0` не делает SDR VMAF модель HDR-совместимой. Зарегистрированный VMAF остается недоступным для сохраненного HDR. Для авторизованного HDR→SDR сравнивайте в пределах преобразованной по Плану SDR области, затем выполняйте визуальную проверку человеком.

Новые пороговые значения или проверки громкости по умолчанию не включены; старые вызовы CLI сохраняют свое поведение при выходе. Действительный VMAF 0/0.5 теперь сохраняется, поэтому старая эвристическая оценка может корректно ухудшаться вместо того, чтобы тихо переключаться на SSIM. Старые JSON загружаются с неустановленными полями доказательств. Пользователи, использующие свои строгие схемы, должны обновить их для новых необязательных полей.

`RunSummary.decode_evidence` является локальным для процесса и проверяется на соответствие идентичности файла (устройство/индекс/размер/время модификации). Запуск/пакет/GUI используют его повторно только для совпадающего вывода; устаревшие токены требуют полной новой декодировки. Это не криптографическое подтверждение и его никогда не следует загружать из ненадежного JSON или хранить как кэш возобновления. Изменение вывода во время QA приводит к `output.changed_during_qa`, а не к успешному результату.

<a id="acceptance-targets"></a>

## Критерии приёмки

Проект не публикует универсальные пороговые значения для pHash, Chromaprint, SSCD или устаревшего поля `cid_predict_self`. Они варьируются в зависимости от выборки, выравнивания и контента, а также не измеряют перцептивное качество. Производственное принятие начинается с проверки корректности медиа, затем используется зарегистрированный VMAF/SSIM/PSNR и аудио LUFS/истинный пик на лицензированной коллекции естественного контента. Поля сходства остаются отдельной диагностикой.

<a id="reading-the-heatmap"></a>

## Чтение тепловой карты

HTML отображает выборочные окна, окрашенные по визуальному сходству. Аудио появляется в окне только тогда, когда одно окно охватывает весь измеренный префикс. Общий балл также включает агрегированное аудио, если оно доступно. Отсутствующее аудио исключается из словаря окон и отображается как недоступное, а не как ноль.

Общий префикс заканчивается на самом коротком файле или через 600 секунд. Более длинные хвосты не измеряются. Окна делят этот префикс (до 150 окон, максимум 600 визуальных образцов), включая остаточную длительность; они не являются непрерывным анализом. Сырой ретайминг не выравнивается автоматически. Запрошенные времена выборки имеют разрешение каденции, и каждый сравниваемый файл использует одинаковый абсолютный визуальный диапазон:

```
[█][█][░][▒][█][▒][░][░][█][▒]  ← time →
 green = lower heuristic similarity     red = higher heuristic similarity
```

Устаревшее поле **weakest chunk** указывает на образец с наибольшим сходством. Общие диагностические шаблоны:

- Одиночный блок с высокой схожестью в начале обычно соответствует логотипу/титульной карточке и должен быть проверен на правильное временное соответствие.
- Непрерывная полоса может указывать на статический контент или проблему с выборкой/выравниванием.
- Низкая схожесть не означает хорошее качество; проверяйте зарегистрированные метрики качества и визуализированный контент отдельно.

<a id="standalone-qa-no-encode"></a>

## Отдельная проверка качества (без кодирования)

```bash
video-uniq qa /path/to/master.mp4 /path/to/candidate.mp4 --vs-corpus
# writes candidate.mp4.qa.json + candidate.mp4.qa.html
```

`--vs-corpus` добавляет раздел `corpus_matches`, чтобы вы могли проверить, не слишком ли кандидат похож на ранее загруженный вариант.

Отдельная проверка качества никогда не предполагает преобразования, семена или сегментацию. Для запроса зарегистрированных метрик сериализуйте точно завершенный `RunSummary.plan` и предоставьте тот же сегментный таргет, который сгенерировал вывод:

```python
Path("completed-plan.json").write_text(summary.plan.model_dump_json(indent=2))
```

```bash
video-uniq qa master.mp4 candidate.mp4 \
  --plan-json completed-plan.json \
  --registration-segment-sec 600
```

Без `--plan-json` все зарегистрированные поля остаются пустыми, а сырые метрики не изменяются.

<a id="fast-qa"></a>

## Быстрая проверка качества

Для пакетной обработки, когда VMAF не нужен (медленно):

```bash
video-uniq run … --fast-qa
# - skips VMAF (the slowest stage)
# - halves the phash sample count
```

Форма JSON идентична, с `vmaf_mean = null` и `phash_samples ≈ 60`.

<a id="programmatic-access"></a>

## Программный доступ

```python
import json
from pathlib import Path

qa = json.loads(Path("out.mp4.qa.json").read_text())

# Internal audio fingerprint diagnostic:
hp = qa.get("audio_fp_hamming_per_frame")
if hp is not None:
    print(f"Audio FP distance: {hp:.1f} bits/frame")

# Worst chunk:
worst = max((c["combined"] for c in qa["chunk_similarities"]), default=None)
print("worst sampled similarity:", worst)
```

Модель Pydantic является `video_uniquifier.core.models.QAReport`, если вы предпочитаете работать с типизированными объектами.

Для стратифицированного объединения источников длиннее 600 секунд агрегированные аудиорасстояния остаются доступными, но регистрация физического смещения/дрейфа временной шкалы недоступна. Смещение на стеженном отпечатке не может быть преобразовано в часы всего фильма.

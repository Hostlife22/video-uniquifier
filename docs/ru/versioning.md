# Версии и совместимость

Проект следует [Семантическому Версионированию 2.0.0](https://semver.org/) для каждого контракта, указанного в [API Контрактах](api-contracts.md). Публичный API:
**стабильный**: код, который импортирует `video_uniquifier.core` или вызывает
`video-uniq` из скрипта оболочки, может зафиксировать `video-uniquifier~=2.2` и получать обновления в ветке 2.x с сохранением совместимости. Версия 2.0.0 вводит новые пакет, импорт, команды и имена переменных окружения; обновите интеграции при переходе с предыдущей мажорной версии.

<a id="what-counts-as-a-breaking-change"></a>

## Что считается изменением с нарушением совместимости

Изменение является **МАЖОРНЫМ** (1.x → 2.0), когда оно делает одно из следующего с контрактом, помеченным `stable`:

|Поверхность|Разрушающее действие|
|---|---|
| `core.Plan`, `core.Profile`, `core.SourceMeta`, `core.EncoderCandidate` |Удаление поля; переименование поля; ужесточение типа (например, `int | None` → `int`); изменение стандартной семантики|
| `core.RunEvent.kind` |Удаление литерала `kind`; изменение схемы полезной нагрузки существующего `kind`|
| `core.RunOptions`, `core.RunSummary` |Удаление поля; переименование; уточнение типа|
|Группа точки входа плагина `video_uniquifier.transforms`|Изменение протокола, которому должны соответствовать зарегистрированные преобразования|
|CLI: `video-uniq <subcommand>`|Удаление подкоманды; удаление или переименование флага; изменение контракта кода выхода|
|Схема профиля YAML|Удаление ключа верхнего уровня; переименование идентификатора преобразования; уточнение `extra=forbid` для отклонения ранее допустимых форм|
|Точки входа Python API: `build_plan`, `run_full`, `compute_plan_hash`|Изменение сигнатуры вызова неаддитивным образом|
|`Plan` JSON сериализация|Поле, которое проходило циклическую сериализацию в N.Y.Z, больше не проходит в (N+1).0.0|

Изменение считается **MINOR** (1.0 → 1.1), если оно делает любое из следующего:

- Добавляет новое необязательное поле с разумным значением по умолчанию в стабильную модель
- Добавляет новый литерал `RunEvent.kind`
- Добавляет новую подкоманду CLI, флаг или переменную окружения
- Добавляет новый поставляемый YAML-профиль
- Добавляет новое преобразование (зарегистрированное в `core/transforms/__init__.py`)
- Помечает любое из вышеуказанного как устаревшее (но не удаляет); выводит
  `DeprecationWarning` как минимум на один полный MINOR цикл перед удалением

Изменение является **PATCH** (1.0.0 → 1.0.1), когда оно только исправляет баги: поверхность контракта не меняется, поведение под задокументированными инвариантами восстанавливается согласно задокументированному контракту.

<a id="stability-labels"></a>

## Метки стабильности

Каждое поле модели и флаг CLI несет одну из трех меток в [API Contracts](api-contracts.md):

- **`stable`** — покрывается обязательствами SemVer, указанными выше.
- **`experimental`** — покрывается обязательствами, но MINOR может удалить его с помощью `DeprecationWarning`. Используйте на свой риск; закрепляйте на точных патч-версиях, если вы зависите от экспериментальной поверхности.
- **`internal`** — не покрыто. Всё в модулях `_*`,
  `video_uniquifier.core._internal` или помечено как внутреннее в [API Contracts](api-contracts.md). Может изменяться в любом релизе.

Часть API, которая **не имеет метки** в [API Contracts](api-contracts.md), по умолчанию является **`internal`**. Если вы хотите на неё полагаться, откройте RFC с запросом на продвижение.

<a id="rfc-process-for-breaking-changes"></a>

## RFC для изменений с нарушением совместимости

Мы осторожны с MAJOR обновлениями. Любой PR, который намерен нарушить контракт `stable`, должен:

1. **Сначала открыть RFC.** Создайте обсуждение на GitHub в категории "RFCs" используя [шаблон RFC](https://github.com/hostlife22/video-uniquifier/issues/new?template=rfc.yml). Формат заголовка: `RFC: <short summary>`.
2. **Укажите четыре обязательные секции** в шаблоне:
   - **Проблема.** Какое текущее поведение неверное, отсутствует или
     доставляет неудобства. Включите конкретные видимые пользователю симптомы или кейсы использования.
   - **Предложение.** Точный новый контракт — подписи полей,
     изменения фильтровой строки, форма CLI. PR может прототипироваться позже,
     но RFC должен зафиксировать форму.
   - **Альтернативы.** Какие дополнительные (не разрушающие) подходы были
     рассмотрены и почему они были отклонены.
   - **План миграции.** Что пользователям нужно сделать для обновления. Включите
     пути устаревания, если возможно (предупреждать одну MINOR-версию, удалить в
     следующей MAJOR-версии).
3. **Открыто минимум 7 дней.** RFC не могут быть приняты до истечения 7 календарных дней после открытия обсуждения. Это дает пользователям из разных часовых поясов возможность высказаться.
4. **Подтверждение мейнтейнера.** Мейнтейнер комментирует
   `accepted` или `rejected`, когда консенсус ясен. Принятый RFC разблокирует PR с меткой `breaking-change`.
5. **Запись CHANGELOG.** Каждое принятое изменение с нарушением совместимости получает отдельный пункт под заголовком `### Removed` или `### Changed` в блоке следующего MAJOR-релиза, включая ссылку на RFC.

Тривиальные изменения с нарушением совместимости (например, прекращение поддержки Python 3.10 после его окончания поддержки) все равно требуют RFC, но RFC, подготовленные мейнтейнерами, могут использовать сокращенный 3-дневный период для комментариев.

<a id="supported-versions"></a>

## Поддерживаемые версии

|Строка версии|Статус|Исправления ошибок|Исправления безопасности|До|
|---|---|---|---|---|
|**2.2.x**|Активная|да|да|Будет определено — см. GitHub Releases|
|2.1.x и ранее|Конец поддержки|нет|нет|заменено|

Исправления безопасности для активной ветки выпускаются как версии PATCH в течение 30 календарных дней после подтверждения раскрытия КРИТИЧЕСКОЙ или ВЫСОКОЙ уязвимости. См. [SECURITY.md](https://github.com/hostlife22/video-uniquifier/blob/main/SECURITY.md) для политики раскрытия.

<a id="python-version-policy"></a>

## Политика версий Python

Версия 2.2.0 требует Python 3.11 или новее. В CI тестируются Python 3.11 и 3.12 на Ubuntu, macOS и Windows. Более новые интерпретаторы не охвачены этой матрицей, пока не будут явно добавлены. Изменение минимальной поддерживаемой версии Python требует RFC и задокументированной политики миграции/устаревания для нижестоящих паковщиков.

<a id="profile-yaml-versioning"></a>

## Версионирование YAML профиля

Профили проверяются на соответствие нативной модели `Profile` и схеме параметров каждого преобразования. Отдельного поля `profile_schema_version` в YAML нет; неизвестные ключи отклоняются `extra=forbid`. Версия приложения 2.2.0 не подразумевает версию схемы YAML 2.2.0. Стабильные изменения профиля следуют политике SemVer/RFC и снимкам контрактов, описанным в [контрактах API](api-contracts.md).

<a id="how-to-depend-on-video-uniquifier-safely"></a>

## Как безопасно полагаться на video-uniquifier

|Сценарий использования|Ограничение версии|
|---|---|
|Приложение, вызывающее `video-uniq` из shell-скрипта|`video-uniquifier~=2.2` (МИНОР-стабильный)|
|Библиотека, которая импортирует `video_uniquifier.core` и использует только `stable` поверхность| `video-uniquifier~=2.2` |
|Библиотека, использующая любую `experimental` поверхность|`video-uniquifier==2.2.*` (PATCH-стабильный)|
|Воспроизводимый исследовательский артефакт / статья|Точный пин, например, `video-uniquifier==2.2.0`|
|Редактируемая установка для разработки|`pip install -e ".[dev,gui]"` из рабочей копии|

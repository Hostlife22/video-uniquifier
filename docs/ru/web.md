# Веб-интерфейс и Docker

Безголовый сервер FastAPI, который управляет тем же оркестратором, что используются CLI и настольный GUI. Веб-слой — тонкая оболочка — каждая конечная точка строит `Plan` + `RunOptions` и передает их
`core.orchestrator.run_full`. В `web/` не содержится бизнес-логики.

Предполагаемое развертывание — это домашний NAS: запустите контейнер, смонтируйте вашу медиадерево, выполняйте кодирование с телефона или ноутбука в локальной сети. Обратный прокси спереди (nginx, Caddy, Traefik) обеспечит TLS и более адекватную аутентификацию, чем встроенный обход basic-auth.

<a id="run-it-locally"></a>

## Запустите локально

```bash
pip install video-uniquifier[web]
video-uniq-web                           # binds 127.0.0.1:8080 by default
```

Затем откройте <http://127.0.0.1:8080>.>. Страница является обычным SPA на vanilla-JS (без фреймворка). Выберите путь ввода, профиль из выпадающего списка, при необходимости имя выходного файла — нажмите **Start**. Прямой прогресс передается через Server-Sent Events.

CLI-флаги (эквиваленты через переменные окружения):

|Флаг|Переменная окружения|По умолчанию|
|------------------|--------------------------|-------------------------------|
| `--host`         | `VIDEO_UNIQ_WEB_HOST`       | `127.0.0.1`                   |
| `--port`         | `VIDEO_UNIQ_WEB_PORT`       | `8080`                        |
| `--work-dir`     | `VIDEO_UNIQ_WEB_WORK_DIR`   | `~/.cache/video_uniquifier/web`  |
| `--output-dir`   | `VIDEO_UNIQ_WEB_OUTPUT_DIR` | `./output`                    |
| `--profile-dir`  | `VIDEO_UNIQ_WEB_PROFILE_DIR`|конфигурация XDG для каждого пользователя|
| `--input-root`   | `VIDEO_UNIQ_WEB_INPUT_ROOT` |текущая рабочая директория|
| —                | `VIDEO_UNIQ_WEB_MAX_CONCURRENT_RUNS` | `2`                    |
| —                | `VIDEO_UNIQ_WEB_RUN_RETENTION_SEC` |`604800` (7 дней)|
| —                | `VIDEO_UNIQ_WEB_MAX_RUN_RECORDS` | `1000`                    |

Basic auth требует проверки как `VIDEO_UNIQ_WEB_USER`, так и
`VIDEO_UNIQ_WEB_PASS` устанавливается. Если ни один не установлен, сервер работает в режиме LAN-trust и рассматривает каждый запрос как аутентифицированный — приемлемо только для привязки к loopback или изолированной сети контейнеров. Учетные данные HTTP Basic просто кодируются, а не шифруются: никогда не публикуйте этот сервис напрямую в ненадежной сети. Завершайте TLS и применяйте политику доступа на обратном прокси; привяжите порт на стороне хоста к `127.0.0.1`, когда прокси работает на том же хосте.

## Docker

Поставляемый `Dockerfile` представляет собой сборку в два этапа: сборщик Python wheel и `python:3.12-slim-bookworm` runtime, который устанавливает архитектурно-соответствующие `ffmpeg` и `ffprobe` Debian. Пользователь runtime не является root (`uid 1000 videouniq`); точки монтирования для записи данных заранее созданы, и `tini` убирает зомби-процессы ffmpeg, если контейнер убивается во время кодировки.

Образ сознательно **не** устанавливает дополнительный `[ml]` (`torch` сам по себе ~800 МБ). Если вам нужен SSCD внутри контейнера, создайте свой собственный:

```dockerfile
FROM video-uniquifier:2.2.0
USER root
RUN pip install --no-cache-dir "video-uniquifier[ml]"
USER videouniq
```

<a id="build"></a>

### Сборка

```bash
docker build -t video-uniquifier:2.2.0 .
```

Рабочий процесс выпуска публикует один манифест для `linux/amd64` и `linux/arm64`. Перед публикацией каждая архитектура должна собрать, сгенерировать H.264/AAC тестовый файл, обработать его через `video-uniq`, проверить выходной битовый поток, запустить веб-сервис и передать `/healthz`:

```bash
tools/docker_multiarch_smoke.sh linux/amd64 video-uniquifier:smoke-amd64
tools/docker_multiarch_smoke.sh linux/arm64 video-uniquifier:smoke-arm64
```

Запуск на не-native архитектуре использует QEMU и может быть в несколько раз медленнее, чем нативная сборка. GitHub Actions хранит отдельные кэши BuildKit для каждой архитектуры и повторно использует оба при финальной подписанной сборке для нескольких архитектур.

<a id="run-lan-trust"></a>

### Запустить (LAN доверие)

```bash
docker run --rm -p 127.0.0.1:8080:8080 \
    -v $PWD/input:/data/input:ro \
    -v $PWD/output:/data/output \
    -v $PWD/work:/data/work \
    video-uniquifier:2.2.0
```

<a id="run-behind-a-same-host-tls-reverse-proxy"></a>

### Запустить за обратным прокси TLS на том же хосте

```bash
docker run --rm -p 127.0.0.1:8080:8080 \
    -e VIDEO_UNIQ_WEB_USER=alice \
    -e VIDEO_UNIQ_WEB_PASS=hunter2 \
    -v $PWD/input:/data/input:ro \
    -v $PWD/output:/data/output \
    video-uniquifier:2.2.0
```

Настройте nginx, Caddy или Traefik для предоставления конечной точки `https://` и проксирования на `http://127.0.0.1:8080`. Не изменяйте адрес публикации на `0.0.0.0`, если только внешний межсетевой экран не обеспечивает эквивалентную доверенную границу.

### docker-compose

Справка `docker-compose.yml` поставляется в корне репозитория с привязкой к loopback, монтированием томов для ввода/вывода/рабочих файлов/профилей, а переменные окружения для базовой аутентификации закомментированы. Также применяются стандартные строгие ограничения: 4 ЦП, 12 ГиБ ОЗУ, 512 PID и два параллельных запуска веб-версии. Значение ОЗУ по умолчанию включает запас по сравнению с наблюдаемым ~8.8 ГиБ пика для 1080p60 HDR/VMAF обработки; на хостах с меньшим объемом памяти следует отключить тяжёлый QA или установить явное меньшее ограничение. Скопируйте его на ваш NAS, отредактируйте пути томов, настройте `VIDEO_UNIQ_CPU_LIMIT`, `VIDEO_UNIQ_MEMORY_LIMIT`,
`VIDEO_UNIQ_PIDS_LIMIT`, и `VIDEO_UNIQ_MAX_CONCURRENT_RUNS` для хоста, затем запустите
`docker compose up -d`. Нативные установки должны обеспечивать эквивалентные строгие ограничения ЦП/ОЗУ через менеджер сервисов операционной системы; `--workers` сам по себе является планировщиком кодировщика, а не пределом памяти.

<a id="api-surface"></a>

## API интерфейс

Каждая конечная точка использует JSON для ввода и вывода, кроме SSE потока событий и QA HTML/JSON passthrough.

|Метод|Путь|Примечания|
|--------|-----------------------------------------------------|-----------------------------------|
| GET    | `/`                                                 |Оболочка SPA (HTML)|
| GET    | `/healthz`                                          |живость; возвращается `ok`|
| GET    | `/api/profiles/local`                               |в комплекте + YAML на пользователя|
| GET    | `/api/profiles/community?refresh=true`              |Каталог маркетплейса|
| POST   | `/api/profiles/community/{id}/install`              |Проверьте SHA + установку|
| POST   | `/api/run`                                          |запустить код; возвращает `run_id`|
| GET    | `/api/run/{id}/events`                              |Поток RunEvents на SSE|
| GET    | `/api/run/{id}/status`                              |Опрос по терминальному состоянию|
| POST   | `/api/run/{id}/cancel`                              |перевернуть CancelToken (честь ≤ 7 s)|
| GET    | `/api/qa/{name}/html`                               |Подавать `<name>.qa.html`|
| GET    | `/api/qa/{name}/json`                               |Подавать `<name>.qa.json`|

`POST /api/run` тело:

```json
{
  "input_path": "/data/input/source.mp4",
  "profile_path": "/data/profiles/cid_aware.yaml",
  "output_name": "optional.mp4",
  "encoder_override": null,
  "workers": 1
}
```

Входные пути вне `WebConfig.input_root` отклоняются с помощью **403**; когда он снят, сервер использует текущую рабочую папку в качестве корня. Установите `--input-root /data/input` явно для монтирования NAS/контейнеров. Попытки обхода пути против
`/api/qa/...` отклоняются с кодом **400 / 404**. Запросы с телом требуют ровно одного действительного неотрицательного `Content-Length`; отсутствующие, неправильные, отрицательные, дублированные или превышающие лимит длины отклоняются до обработки маршрута. Комбинирование `Transfer-Encoding` с `Content-Length` также отклоняется. Тело запроса с разделением на части (chunked) намеренно не поддерживается, чтобы оно не могло обойти установленный жёсткий предел.

Статус выполнения терминала хранится атомарно в `<work-dir>/web_runs.json` и сохраняется при перезапуске процесса. Выполнение, которое было `pending` или `running` при остановке сервера, регистрируется как `failed` с диагностикой прерывания/перезапуска; контрольные точки FFmpeg остаются в каталоге рабочих данных каждого выполнения для проверки оператором. Сохраняются только идентификаторы выполнения, статус, скрытый класс ошибки, временные метки и базовые имена выходных файлов — пути к исходникам/профилям и полные сообщения об исключениях в этот веб-реестр не записываются.

Имя файла вывода по умолчанию использует контейнер выбранного профиля (`.mp4`, `.mkv` или `.mov`). Явно указанное имя файла с несовместимым суффиксом отклоняется до запуска фоновой задачи. Активные финальные выводы резервируются атомарно в
`<output-dir>/.video_uniquifier-reservations/`, поэтому отдельные серверные процессы, использующие общую локальную файловую систему, возвращают **409**, вместо того чтобы записывать один и тот же файл. Точный владелец освобождает свое резервирование в финальном состоянии; мертвый владелец на том же хосте может быть восстановлен. Старые записи с чужого хоста завершаются с ошибкой, так как невозможно доказать живость удаленного процесса. Развертывания с совместным доступом/NFS должны квалифицировать семантику атомарного создания и восстановления для своей файловой системы; эта матрица в настоящее время **НЕ ПРОВЕРЕНА**.

`max_concurrent_runs` применяются ко всем серверным процессам, которые используют один и тот же
`output_dir`. Атомарные слоты владельца и их неизменная ёмкость записываются как активные.
`<output-dir>/.video_uniquifier-admission/`; полный пул возвращает **429**, в то время как недоступный или некорректно настроенный пул возвращает **503**. Каждый экземпляр, который использует эту директорию, должен использовать одно и то же значение. Чтобы изменить его, остановите все такие серверы, убедитесь, что ни один процесс кодирования не активен, удалите только эту директорию допуска, а затем перезапустите серверы с новым общим значением. Умершие владельцы с того же хоста восстанавливаются; владельцы с нарушенной структурой и с других хостов обрабатываются как закрытые.

Каждый вызывающий `run_full` также координирует слоты кодировщика и оценочные байты временного диска через `VIDEO_UNIQ_RESOURCE_LOCK_DIR` (по умолчанию:
`~/.cache/video_uniquifier/resource-admission`). Docker-образ указывает на смонтированный `/data/work/.resource-admission`, поэтому соседние контейнеры должны использовать этот рабочий том совместно, чтобы делить бюджет. Используйте один и тот же абсолютный путь реестра и учетную запись службы для всех локальных экземпляров. Остановите все участвующие процессы перед очисткой или изменением обнаруженной мощности кодировщика.

Это по-прежнему граничная зона безопасности, основанная на оценках, а не планировщик кластера. Смешанная видимость/маршрутизация устройств GPU, разные учетные записи сервисов, атомарность NFS, разрывы в сети и точность естественных оценок битрейта 4K/длительной формы остаются
**НЕ ПРОВЕРЕНО**; обеспечивайте жесткие квоты файловой системы извне в этих развертываниях.

<a id="whats-not-on-the-web-yet"></a>

## Что *еще* не на вебе

* Экраны Калибровка, Пакет, Очередь, Валидация, Корпус — только настольный GUI в v0.9. Веб-оболочка специально ориентирована на сценарий с одним входом «запустить кодек» для NAS-развертываний; полное соответствие экранов запланировано в v1.0.
* На `/` нет обозревателя файловой системы — пути должны вводиться вручную (или вставляться из веб-интерфейса NAS). Селектор в списке желаемого в v1.0.
* Нет повторного подключения SSE при временном сбое. Обновите страницу;
  `run_id` сохраняется на стороне сервера до следующего запуска.

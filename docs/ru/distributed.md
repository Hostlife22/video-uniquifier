# Распределённая обработка

`video-uniq queue` + `video-uniq worker` позволяют нескольким машинам использовать одну очередь задач без внешнего координатора. Координация просто
`os.rename(2)` между двумя каталогами на общей файловой системе.

<a id="filesystem-requirements"></a>

## Требования к файловой системе

Контракт: переименование между каталогами должно быть **атомарным** — точно один исполнитель выигрывает каждую аренду. Совместимые настройки:

|FS / монтирование|Статус|
|---|---|
|**NFSv4** с опцией монтирования `noac`|целевая конфигурация; проверить на реальных хостах перед производством|
|**ZFS** совместно через NFSv4 (`sharenfs=on`)|поддерживается|
|**ext4** на одном хосте (многопроцессное выполнение на одной машине)|поддерживается|
|**APFS** на macOS (тестирование на одном хосте)|поддерживается|
|NFSv3 без `noac`|НЕ поддерживается — кэширование атрибутов делает переименование неатомарным|
|`s3fs-fuse`, `goofys` (S3 через FUSE)|НЕ поддерживается — переименование реализовано как копирование+удаление|
| SMB1 |НЕ поддерживается|
| SMB2/3 |частично; проверяйте с помощью шага `init`|

`video-uniq queue init` выполняет реальный тест атомарного переименования для выбранного каталога и быстро выдаёт понятную ошибку, если файловая система не может выполнить контракт.

<a id="nfs-mount-options-linux"></a>

## Опции монтирования NFS (Linux)

На клиенте:

```
your.nfs.server:/exports/queue  /shared/queue  nfs4  noac,vers=4.2,hard,timeo=600  0  0
```

`noac` отключает кэш атрибутов, который делает `rename` неатомарным для параллельных читателей. Да, это замедляет операции с метаданными — это компромисс для корректного управления арендой.

<a id="workflow"></a>

## Рабочий процесс

```bash
# On one machine (or any one machine that mounts the share):
video-uniq queue init /shared/queue
video-uniq queue add  /shared/queue /shared/sources/movie1.mp4 \
                                  /shared/sources/movie2.mp4 \
                                  /shared/sources/movie3.mp4

# On worker hosts A and B (both mount /shared):
video-uniq worker /shared/queue \
  --profile /shared/profiles/cid_aware.yaml \
  --out-dir /shared/uniq/ \
  --encoder libx264 \
  --workers 4 \
  --heartbeat-sec 30 &

# Monitor from anywhere:
video-uniq queue status /shared/queue --json
# {"pending": 0, "in_progress": 2, "done": 1, "failed": 0}
```

<a id="heartbeat-and-recovery"></a>

## Сигнал жизни и восстановление

Каждый рабочий процесс имеет идентификатор хоста+PID+nonce и обновляет свой файл `.alive` каждые
`--heartbeat-sec` (по умолчанию 30 секунд). Если время изменения файла (mtime) старше, чем
`stale_sec` (по умолчанию 300 секунд, настраивается через `video-uniq queue reset --stale-sec`), следующий `lease()` любого другого исполнителя переместит арендованные файлы этого хоста обратно в `pending/`.

CLI и GUI исполнители поддерживают этот heartbeat, пока FFmpeg активен. Завершённая кодировка сначала записывается в скрытый файл, специфичный для исполнителя, рядом с конечным выходным файлом. Общий оркестратор проверяет его поток/временную метку/цветовой контракт и декодирует полный основной видеопоток плюс все аудиопотоки до того, как исполнитель сможет зафиксировать этот файл. Этот контроль корректности обязателен; подробные отчёты pHash/VMAF/SSIM в формате HTML/JSON остаются отдельной диагностикой и не являются критерием публикации. Исполнитель может опубликовать файл только после атомарного перемещения своей аренды в журнал-специфический скрытый барьер в `done/`; если аренда уже была отозвана при восстановлении очереди, устаревший результат отбрасывается. После публикации этот барьер становится обычным маркером `done/<input>`.

Перед этим ограждением рабочий сохраняет небольшой журнал с контролем доступа под
`<queue>/.commits/`. Если процесс завершится между переименованием аренды в ограждение и окончательным переименованием вывода, другой CLI- или GUI-рабочий ждет, пока исходный сигнал сердцебиения устареет, и публикует уже проверенный подготовленный файл. Случайный токен ограждения принадлежит ровно одному журналу, поэтому более старый маркер `done` с тем же именем или повторно поставленная на очередь жесткая ссылка не могут авторизовать новый вывод. Если аренда была собрана до достижения ограждения, восстановление удаляет незагражденный подготовленный артефакт вместо его публикации.

Это закрывает окно публикации при локальном жестком сбое и обеспечивает обработку с ограждением, как минимум один раз. Это не транзакционная гарантия точно один раз через сетевой разрыв. Развертывания NFS на разных хостах должны по-прежнему запускать проверку лизинга/снятия/журнала/аварийного состояния на фактическом монтировании перед эксплуатацией; эта матрица **НЕ ПРОВЕРЕНА**. Всем рабочим необходим одинаковый UID сервиса или явный наследуемый ACL, предоставляющий требуемый доступ на чтение/запись/удаление к очереди, выходному каталогу, подготовленным файлам и
`.commits/`. Общий GID сам по себе недостаточен для восстановления журналов фиксации. Полезная нагрузка журнала содержит только базовые имена файлов и случайный маркер ограждения, а не абсолютные пути источника/выхода. Журналы неизменяемы после публикации и доступ к ним только у владельца (`0600`, дополнительно ограничено `umask`); восстановление удаляет их записи в каталоге, а не изменяет их содержимое.

<a id="local-nfs-fault-injection-lab"></a>

## Локальная лаборатория инъекции сбоев NFS

Docker на хосте Linux может создать временный NFSv4 сервер и двух независимых клиентов, затем выполнить одновременное управление арендой, сетевое разделение с удалением устаревших данных, блокировку публикации устаревшего владельца и восстановление после SIGKILL на четырех границах публикации (после этапа, журнала, ограждения и публикации). Также проверяется идемпотентное повторное восстановление, отклонение поврежденной контрольной точки и выживание атомарной контрольной точки на ограниченной tmpfs с ENOSPC:

```bash
tools/docker_nfs_fault_smoke.sh
```

Доказательства записываются в `.nfs-qualification/` и включают JSON для каждого сценария, проверку Docker и таблицу монтирования клиента. Лаборатория использует короткий таймаут `soft`, чтобы принудительное разделение не блокировало очистку Docker. Это умышленно отличается от рекомендуемого производственного монтирования `hard` выше: прохождение лаборатории является детерминированным контрольным этапом/ограждением приложения, в то время как реальные производственные хосты должны быть проверены с их фактическим монтированием `hard`, сервером, сетью и политикой восстановления после отказа.

Оригинальная исправленная лабораторная работа прошла проверку на Ubuntu, размещённой на GitHub, в ходе запуска Actions
`33881832592`. Расширенная матрица также прошла проверку локально на Docker Desktop/Intel macOS, включая проверку уникальности аренды в многопоточном режиме, удаление устаревших данных/блокировки и продолжение после восстановления клиентского TCP/2049. Это сохранённые результаты временной лаборатории, а не подтверждение действительного развертывания NFS-сервера или вариантов монтирования.

<a id="per-machine-encoder-variation"></a>

## Вариации кодировщика на каждой машине

По замыслу, два рабочих могут использовать **разные** кодировщики (один libx264 на Linux, другой hevc_videotoolbox на Mac). В результате варианты одного и того же исходного материала немного отличаются в параметрах потока H.264 / HEVC. Обычно это нормально для случая с дивергенцией CID (варианты должны отличаться). Если нужна согласованность, закрепите всех рабочих на одном кодировщике через `--encoder libx264`.

<a id="output-collisions"></a>

## Конфликты вывода

Рабочие публикуют в `out_dir/<input.stem>.uniq.<profile-container>`. Вставка в очередь отклоняет повторяющиеся имена файлов, но независимые корни очереди всё ещё могут нацеливаться на одну и ту же выходную директорию и соревноваться по одинаковым основам. Избегайте такой ситуации развертыванием:

1. Обеспечив уникальные имена файлов в `pending/`, или
2. Установив для каждого рабочего `--out-dir` и объединив позже.

<a id="docker-compose-example"></a>

## Пример Docker Compose

```yaml
services:
  worker:
    image: video-uniquifier:2.2.0
    volumes:
      - /mnt/shared:/shared:rw            # NFSv4 noac mount on host
    environment:
      VIDEO_UNIQ_PROFILE: /shared/profiles/cid_aware.yaml
    command:
      - video-uniq
      - worker
      - /shared/queue
      - --profile=/shared/profiles/cid_aware.yaml
      - --out-dir=/shared/uniq
      - --encoder=libx264
      - --workers=4
    deploy:
      mode: replicated
      replicas: 4                          # 4 workers in this stack
```

<a id="cleanup"></a>

## Очистка

`done/` — это просто маркер — файлы накапливаются. Периодически:

```bash
find /shared/queue/done -mtime +30 -delete
```

Не удаляйте маркер `done/`, пока соответствующий файл остаётся в `<queue>/.commits/`: маркер — это граница публикации. Здоровые рабочие приводят журналы в соответствие после таймаута сигнала владельца, задолго до 30-дневного примера окна хранения.

(Подкоманда `video-uniq queue prune --done-older-than 30d` отложена до версии v0.4 — до появления настоящей проверки CID работа над ней не ведется. Используйте фрагмент `find` выше в cron до тех пор.)

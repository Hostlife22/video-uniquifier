# Требования YouTube

`video-uniq preflight` проверяет исходник + профиль на соответствие рекомендованным YouTube настройкам кодирования перед запуском и на корректность HDR.

<a id="what-the-matrix-checks"></a>

## Что проверяет матрица

|Код|Степень серьезности|Срабатывает при|
|------|----------|----------------|
| `container.ok` / `container.unsupported` |ок / предупреждение|Исходный контейнер не в `{mp4, mov, mkv}`|
| `video.codec.ok` / `video.codec.unusual` |ок / предупреждение|Исходный видеокодек не входит в `{h264, hevc, vp9, av1}`|
| `video.missing` |сбой|Нет видеопотока в источнике|
| `audio.missing` |предупреждение|Нет аудиопотока — выход будет только с видео|
| `audio.codec.unusual` |предупреждение|Исходный аудиокодек не входит в `{aac, opus, mp3}` (будет перекодирован в AAC)|
| `audio.sr.bad` |предупреждение|Частота дискретизации ≠ 44.1k / 48k (YouTube выполнит пересэмплирование)|
| `fps.ok` / `fps.unusual` |ок / предупреждение|FPS не в пределах ±0.1 от `{23.976, 24, 25, 29.97, 30, 50, 59.94, 60}`|
| `subs.image_based` |предупреждение|Присутствуют субтитры PGS/DVB — нельзя скопировать в mp4, будут удалены|
| `hdr.color.transforms` |**сбой**|HDR-источник + профиль имеет цветовые/эквалайзерные/шумовые преобразования без `keep_hdr=true` **и** без `video.tonemap_sdr` включенных (либо сохранить HDR через обертку zscale, либо преобразовать в SDR через тонемап)|
| `hdr.unsupported.encoder` |**сбой**|HDR источник + кодировщик — libx264 (нет 10-битного профиля), и профиль сохраняет HDR (обходной путь: включите `video.tonemap_sdr` для SDR вывода или выберите `libx265`/HEVC кодировщик)|
| `loudnorm.ok` / `loudnorm.missing` |ок / предупреждение|Профиль не содержит `audio.loudnorm` — вывод не достигнет -14 LUFS|
| `bitrate.over` |предупреждение|Прогнозируемая скорость передачи данных > максимальной для YouTube для данного разрешения|

<a id="h264-output-structure"></a>

## Структура вывода H.264

Квалифицированный путь `libx264` явно создаёт структуру загрузки на YouTube согласно документации:

- прогрессивный вывод 4:2:0 из существующего видео-пайплайна;
- High Profile и кодирование энтропии CABAC;
- не более двух последовательных B-кадров;
- закрытый GOP с максимальным размером половины нативной частоты кадров (`12` кадров при 23.976/24 FPS, `13` при 25 FPS, `15` при 29.97/30 FPS и `30` при 59.94/60 FPS).

Фактическая проверка регрессии потока битов проверяет профиль, выполнение B-кадров, каденцию IDR и CABAC. Изменение этой внутренней политики кодировщика увеличивает ревизию политики контроля хэша плана, поэтому возобновление не может комбинировать сегменты, закодированные по разным правилам GOP.

H.264 VideoToolbox запрашивает ту же общую структуру и проверяется для High, CABAC, закрытой каденции IDR с половиной FPS и ограниченной перестановки B-кадров. FFmpeg предоставляет переключатель перестановки кадров Apple через любое положительное значение `-bf`, а не надежное точное количество: квалифицированное оборудование Intel выдает последовательности из одного B-кадра, а Apple Silicon runner на GitHub выдает последовательности из трех. Поэтому не утверждается, что это эквивалентно byte-for-byte или по шаблону B с libx264. NVENC, QSV и AMF остаются
**НЕ ПРОВЕРЕНО**. Принятие аргументов `-g`/`-bf` недостаточно: каждый бэкенд должен доказать свой вывод на соответствующем физическом оборудовании.

<a id="hevc-and-av1-random-access"></a>

## HEVC и AV1 с произвольным доступом

Документированная YouTube загрузка с половинной частотой кадров для GOP применяется конкретно к H.264. Проект не представляет это правило как требование загрузки для HEVC/AV1. Вместо этого HEVC и AV1 используют внутренний максимальный GOP на две секунды, чтобы сделать поиск, восстановление сегментов и последующую проверку предсказуемыми:

- libx265 и HEVC VideoToolbox выдают закрытые IDR GOP;
- SDR HEVC VideoToolbox явно использует Main/8-бит, а HDR использует Main10/10-бит;
- SVT-AV1 и libaom-AV1 выдают вывод с Main-профилем 4:2:0 с тем же ограничением GOP;
- Режим постоянного качества libaom использует `-b:v 0` без несовместимых опций VBV.

Эти пути протестированы с битстримом на квалифицированном Intel Mac; три программных пути также проходят в производственном контейнере Debian 12. NVENC/QSV/AMF и AV1 VideoToolbox остаются предметами квалификации для оборудования.

<a id="bitrate-ceilings-h264"></a>

## Потолки битрейта (h264)

|Максимальная высота|Потолок|
|------------|---------|
|≤ 1080p|12 Мбит/с|
|≤ 1440p|24 Мбит/с|
|> 1440p (например, 2160p)|68 Мбит/с|

Проверка сравнивает с `source.video[0].bit_rate × 1.25`, так как энкодер выделяет ~25% резерв выше источника.

<a id="loudness-target"></a>

## Целевой уровень громкости

Цель по умолчанию — **-14.0 LUFS интегрированно** (громкость контента YouTube). Установлено в `Profile.target_loudness_lufs`; `audio.loudnorm` соблюдает его.

<a id="when-fail-is-returned"></a>

## Когда возвращается ошибка

`video-uniq run` прерывает работу до начала кодирования, если предварительная проверка возвращает результат с
`severity=fail`. Переопределите с помощью `--no-preflight` (только предупреждения), если вы понимаете, что делаете.

`video-uniq preflight` завершает работу с кодом 1 при ошибке (поэтому подходит для CI).

# Профили

Профиль — это YAML-файл, который описывает, какие преобразования применяются и с какой интенсивностью. Профили находятся в `src/video_uniquifier/profiles/` и могут быть загружены по пути.

<a id="yaml-schema"></a>

## Схема YAML

```yaml
name: string                                                  # required
description: string                                           # optional
transforms:                                                   # list
  - id: <transform.id>                                        # see Transform reference
    enabled: bool                                             # default true
    params: { ... }                                           # validated by the transform's schema
audio_tracks: "first" | "all" | [int, ...]                  # list = absolute ffprobe stream indices
keep_hdr: bool                                                # default false
output_container: "mp4" | "mov" | "mkv"                       # default mp4
target_codec: "h264" | "hevc" | "av1"          # v1.2.0 Task 22 added av1
target_loudness_lufs: float                                   # default -14.0
seed: int | null                                              # used when seed_strategy=fixed
seed_strategy: "fixed" | "per_run" | "per_file" | "divergent" # default per_run; v0.3.3 CID profiles ship divergent

# --- v0.8.0 R3 — segmentation strategy ---
segmentation:
  mode: "keyframe" | "scene"                                  # default keyframe
  scene_threshold: float                                       # default 27.0 (PySceneDetect ContentDetector)
  scene_min_length_sec: float                                  # default 2.0
# --- v0.8.0 R5 — per-segment VMAF target-quality ---
target_vmaf: float | null                                      # default null (loop disabled)
target_vmaf_step: int                                          # default 2 (CRF decrement per retry)
target_vmaf_max_retries: int                                   # default 2 (cap on re-encode attempts)
```

Неизвестные верхнеуровневые поля отклоняются (`extra=forbid`).

`audio_tracks: first` выбирает первый найденный аудиопоток, `all` — все потоки в исходном порядке. Явный список задаёт абсолютные индексы `ffprobe`/`SourceMeta.audio[].index`; результат следует порядку списка, а недопустимые индексы отклоняются до кодирования. Эффекты применяются к первой выбранной дорожке. Остальные копируются, если кодек совместим с контейнером, либо перекодируются согласно правилам мультиплексирования.

`video.crop_resize.max_strength` — это максимальная **общая** доля, удаляемая по каждой оси. Например, `0.06` удаляет не более 6% ширины суммарно по левому и правому краю, а не 6% независимо с каждой стороны. Выходной SAR сбрасывается на 1:1 после масштабирования.

<a id="segmentation-modes-v080-r3"></a>

### Режимы сегментации (v0.8.0 R3)

* **`keyframe`** — режим по умолчанию: границы сегментов совпадают с ключевыми кадрами исходника, поэтому извлечение выполняется копированием потока. Этот режим используют готовые профили.
* **`scene`** — [ContentDetector из PySceneDetect](https://github.com/Breakthrough/PySceneDetect) определяет сцены, затем границы сдвигаются назад до ближайших ключевых кадров для безопасного копирования потока. Если пригодных границ не осталось, используется один сегмент. Требуется `[scene]`: `pip install 'video-uniquifier[scene]'`.

<a id="per-segment-vmaf-target-quality-v080-r5"></a>

### Целевое качество VMAF для каждого сегмента (v0.8.0 R5)

При заданном `target_vmaf` сегмент повторно кодируется с уменьшением CRF на `target_vmaf_step`, пока VMAF не достигнет цели либо не будут исчерпаны `target_vmaf_max_retries`. Базовая подсказка CRF — 18 для x264/x265; аппаратные кодировщики отображают изменение на собственные параметры: NVENC `cq`, QSV `global_quality`, AMF `qp`. При исчерпании попыток сохраняется кандидат с наибольшим измеренным качеством.

Распределённые исполнители сохраняют `target_vmaf` и выполняют тот же ограниченный цикл по сегментам. Защита от эталона без пространственно-временного совмещения всё ещё применима перед кодированием.

См. [seed_strategy.md](seed_strategy.md), чтобы узнать, что означает каждая стратегия и когда какую выбирать.

### Профили целевых платформ (v0.7.0)

Профили фиксируют соотношение сторон для выбранной платформы. Они сочетают `video.fit_aspect` с мягкими преобразованиями изображения и подходящей целевой громкостью `audio.loudnorm`. Исходник можно вписать в вертикальный или квадратный холст без ручного построения команды FFmpeg.

Готовые профили доставки явно задают `allow_upscale: true`, поскольку обещают указанное в таблице разрешение. Пользовательский `video.fit_aspect` по умолчанию использует `allow_upscale: false`: crop выбирает наибольший чётный прямоугольник нужного формата в пределах исходника и заданных ограничений; режимы padding могут расширять холст, но не увеличивают исходное изображение. Включайте `true` только ради обязательного фиксированного холста. Увеличение разрешения не восстанавливает детали.

| `youtube_1080p.yaml`     | 16:9 | `crop`     | 1920×1080 | -14 |Стандартная загрузка на YouTube|

Бизнес-правила, заголовки и логотипы настраиваются по отдельной схеме; см. [подготовку Reels](facebook-reels.md) и примеры в `examples/facebook_reels/`.

<a id="av1-family-v120-task-22"></a>

### Семейство AV1 (v1.2.0 Задача 22)

AV1 доступен как опциональный кодек для доставки. Фактический размер, качество и время кодирования зависят от кодировщика и источника и должны быть проверены; фиксированные проценты или предпочтения платформ не предполагаются. Профили нацелены на `av1` —
`pick_encoder()` по умолчанию использует политику `quality`: `libaom-av1`, затем
`libsvtav1`, затем проверенный аппаратный кодировщик. `balanced` предпочитает SVT-AV1 и
`speed` предпочитает проверенные NVENC/QSV/VideoToolbox/AMF; настройте их с помощью
`VIDEO_UNIQ_ENCODER_POLICY`. `av1_vulkan` не рекламируется, так как существующий граф фильтров CPU-frame не имеет проверенного пути Vulkan `hwupload`. Масштаб CRF — 0..63 с значением по умолчанию 30; качество и скорость не численно эквивалентны CRF x264 и требуют контрольного тестирования, специфичного для контента.

|Имя|Цель|Режим|Разрешение| LUFS |Примечания|
|------|--------|------|------------|------|-------|
| `youtube_av1.yaml`       | 16:9 | `crop`     | 1920×1080 | -14 |AV1 1080p; протестируйте выбранный кодировщик по сравнению с контролем|
| `youtube_4k_av1.yaml`    | 16:9 | `crop`     | 3840×2160 | -14 |AV1 4K; явное полотно может увеличивать мелкие источники|

Проект не заявляет диапазоны VMAF для профилей до проверки на лицензированном корпусе естественных видео с пространственно-временным совмещением эталонов.

⚠️ **HDR и `pad_blur`:** фильтр `gblur` не учитывает HDR. Сначала преобразуйте PQ/HLG в SDR через `video.tonemap_sdr` либо используйте `crop`/`pad_black`. Preflight выдаёт `FAIL` для несовместимого сочетания до начала кодирования.

<a id="writing-your-own-profile"></a>

## Создание собственного профиля

1. Скопируйте `soft.yaml` или `medium.yaml` в `my_profile.yaml`. Начинайте с наименьшего набора преобразований, который соответствует редакционным требованиям авторизованного производного материала.
2. Переключите `enabled` и настройте `params`.
3. Запустите с `video-uniq run --profile my_profile.yaml …`.
4. Проверяйте `<output>.qa.html`. Корректность должна быть подтверждена перед интерпретацией качества или внутренних диагностик сходства. Не применяйте порог VMAF до тех пор, пока пара источник/выход не будет иметь корректную временную и пространственную синхронизацию.
5. Для автоматической настройки интенсивности используйте `video-uniq calibrate` — см. [calibrate.md](calibrate.md).

<a id="notes"></a>

## Примечания

- Поле `seed` используется `video.crop_resize.rng_seed`, когда установлено; одинаковое значение seed → идентичный граф фильтров, полезно для воспроизводимости.
- `audio.loudnorm` — это **двухпроходный** фильтр: первый проход измеряет весь источник, а результат кэшируется в `state.json`, поэтому повторные запуски его пропускают.
- `video.blend_b` требует путь к видео B. Передайте его через `--b-video <path>` в CLI; значение внедряется в параметры преобразования во время выполнения.

<a id="performance-notes"></a>

## Примечания по производительности

- **`audio.pitch_tempo` с `method: rubberband`** (используется устаревшими `cid_aware` и `cid_aggressive`) работает примерно в 5–10 раз медленнее, чем по умолчанию
  `asetrate+atempo` путь. Rubberband сохраняет форманты — важные для голосового контента — но на длинных клипах аудиопоток может работать в 10–20 раз медленнее реального времени вместо <1× реального времени. Замер от 2026-05-31 показал, что 90-секундный клип × `cid_aware` × `libx264` обрабатывался примерно 18 минут на 8-ядерном Mac. Для пакетной обработки не голосового контента предпочтительно
  `medium` / `aggressive` (которые опускают флаг `method: rubberband` и переключаются на путь atempo).
- **Предварительная проверка требует фильтров `rubberband` и `zscale`**, когда профиль использует их. Проверка сухого запуска в начале работы завершается быстро (<1 с), если ffmpeg не содержит `librubberband` (используется путем изменения высоты Rubberband) или
  `libzimg` (используется `video.tonemap_sdr` и `keep_hdr: true`). Стандартная версия ffmpeg из Homebrew не включает ни одного из них — установите через
  `brew install ffmpeg --HEAD` или соберите из исходников с помощью
  `--enable-librubberband --enable-libzimg`.

<a id="rubberband-performance-characteristic"></a>

### Характеристики производительности Rubberband

Матрица реального видео от 2026-05-31 (`docs/bug-triage-2026-05-31.md` §9) измеряла затраченное время на выполнение для всех комбинаций профиля × входных данных на
`evermeet.cx` ffmpeg 8.1.1 + `librubberband` + `libzimg` + `libvmaf`, один рабочий процесс, `libx264`. Цифры указаны в секундах по настенным часам:

|Профиль|clip_a 30 с|clip_long 90 с|synth_sdr_4k 12 с|synth_long_5min 300 с|
|---              |---:         |---:            |---:               |---:                   |
| `soft`          | 17          | 37             | —                 |136 (запуск) + 326 (возобновление)|
| `medium`        | 17          | 39             | —                 | 145                   |
| `aggressive`    | 20          | 46             | —                 | 242                   |
| `cid_aware`     | 224         | 623            |ПРЕВЫШЕНО ВРЕМЯ (>1800)|ПРЕВЫШЕНО ВРЕМЯ (>1800)|
| `cid_aggressive`| 316         | 871            |ПРЕВЫШЕНО ВРЕМЯ (>1800)|ПРЕВЫШЕНО ВРЕМЯ (>1800)|

`cid_aware` / `cid_aggressive` запуск ~10–15× дольше времени настенных часов, чем
`soft` / `medium` / `aggressive` на том же контенте. Аудио-цепочка rubberband является однопоточной внутри ffmpeg и выполняется последовательно с (параллельной) видео-цепочкой, поэтому на источниках `>60 s` или `>1080p` проход по аудио занимает основное время по настенным часам. Выбор сделан специально:

- **Сохраняйте `rubberband`**, когда сохранение формант важнее скорости — голосовой контент, подкасты, видео с говорящим человеком, все, где "эффект бурундука" `asetrate` был бы неприемлем.
- **Не выбирайте величину питча из внешнего порога сопоставления.** Используйте только редакционно обоснованную величину и проверяйте качество речи/музыки прослушиванием.
- **Переключитесь на `asetrate`**, когда важнее пропускная способность — B-roll, контент только с музыкой, пакетная обработка больших файлов. Редактируйте YAML-профиль на месте или сохраните производную копию:

```yaml
# my_fast_derivative.yaml — legacy profile with the asetrate fallback
transforms:
  - id: audio.pitch_tempo
    enabled: true
    params: {pitch: 1.06, randomize_within: 0.005, method: asetrate}
```

`preflight()` генерирует `audio.pitch.rubberband.slow` (уровень серьёзности=`warn`) при запуске профиля с поддержкой rubberband на исходном `>60 s` или
`>1080p`, чтобы стоимость на стене отображалась до начала кодирования. WARN носит информационный характер — кодирование всё равно продолжается. Реализовано в
`src/video_uniquifier/core/preflight.py::_check_rubberband_perf`.

_(Измерено 31.05.2026 на `evermeet.cx` ffmpeg 8.1.1 + librubberband на 8-ядерном Mac. Измерять снова ежегодно или после крупного обновления ffmpeg.)_

<a id="legacy-high-change-profiles"></a>

## Устаревшие профили с высокой изменчивостью

`cid_aware` и `cid_aggressive` сохраняют свои идентификаторы, чтобы существующие сохраненные задания и автоматизация продолжали загружаться. Это экспериментальные наборы эффектов, а не стандартные настройки производственного качества. Их операции с тоном, временной, фазой, динамикой и шумом могут быть видимыми или слышимыми и требуют проверки на собственном или лицензированном контенте.

pHash, сходство аудио и SSCD используются только для внутренней диагностики регрессий и сравнения собственных вариантов. Они не предсказывают и не гарантируют поведение YouTube Content ID или других внешних систем защиты прав.

При заданном `target_vmaf` сегмент повторно кодируется с уменьшением CRF на `target_vmaf_step`, пока VMAF не достигнет цели либо не будут исчерпаны `target_vmaf_max_retries`. Базовая подсказка CRF — 18 для x264/x265; аппаратные кодировщики отображают изменение на собственные параметры: NVENC `cq`, QSV `global_quality`, AMF `qp`. При исчерпании попыток сохраняется кандидат с наибольшим измеренным качеством.
`quality.target_vmaf.unregistered_reference`. Текущая обратная связь может настраивать только CRF энкодера; она не может интерпретировать незарегистрированное сравнение источника/выхода как качество сжатия. Запустите зарегистрированную последующую проверку качества (QA) вместо этого.
